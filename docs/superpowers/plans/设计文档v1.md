## 一、项目背景与目标

### 1.1 背景
用户（AI产品经理）每次面试后需要做深度复盘，当前靠手动整理效率低。需要一个自动化Skill，输入「简历PDF + 岗位介绍 + 面试录音文字稿」，一键输出结构化的面试复盘Markdown文档。

### 1.2 目标
- **效率提升**：原本30-60分钟的手动复盘，AI 5分钟内完成
- **结构化输出**：严格按照用户定义的文档结构和评分标准生成
- **可追溯**：中间每一步的结构化数据可选保存，方便debug和验证AI提取质量
- **可扩展**：V1为纯Markdown，V2可无缝扩展飞书同步、HTML可视化、复盘数据库等

### 1.3 用户输入资料
| 资料 | 格式要求 | 是否必须 |
|---|---|---|
| 简历PDF | PDF（可脱敏） | 必须（缺则追问，允许跳过但理想回答降级为通用框架） |
| 岗位介绍 | 直接粘贴文本 / 图片 / PDF / Word | 必须（缺则追问） |
| 面试录音文字稿 | PDF / Word / TXT | 必须（缺则追问） |

## 二、架构方案：方案D（混合模式）

### 2.1 方案选型理由
- **脚本处理脏活**：PDF解析、文件名正则提取、文本粗清洗等确定性逻辑，用Python精确控制
- **Prompt处理智能活**：语义理解、QA拆分、分类评分、理想回答生成等AI推理，用LLM分阶段完成
- **两者结合**：脚本预处理降低LLM负担，让AI更聚焦在语义理解上，输出质量更稳定

### 2.2 与其他方案的对比
| 维度 | 方案D（选中） | 方案B：纯Prompt Chain | 方案C：全脚本 |
|---|---|---|---|
| PDF解析质量 | ⭐⭐⭐⭐⭐ 脚本预处理+正则清洗 | ⭐⭐⭐ 直接喂给LLM | ⭐⭐⭐⭐⭐ 同D |
| 文件名元信息提取 | ⭐⭐⭐⭐⭐ 正则精确匹配 | ⭐⭐⭐ LLM猜可能不准 | ⭐⭐⭐⭐⭐ 同D |
| 中间过程可debug | ⭐⭐⭐⭐⭐ JSON落盘 | ⭐⭐ 黑盒 | ⭐⭐⭐⭐⭐ 同D |
| 代码维护量 | ⭐⭐⭐ 少量脚本 | ⭐ 零代码 | ⭐⭐⭐⭐⭐ 大量脚本 |
| 输出稳定性 | ⭐⭐⭐⭐⭐ 最优 | ⭐⭐⭐ 中等 | ⭐⭐⭐⭐ 高 |

## 五、各模块详细设计

### 5.1 脚本层 scripts/

#### 5.1.1 parse_files.py —— 统一文件解析入口
**功能**：接收用户上传的3个文件路径，批量解析并清洗，输出预处理后的4份干净数据。

| 输入参数 | 类型 | 说明 |
|---|---|---|
| resume_path | string | 简历PDF文件路径 |
| job_desc_path | string | 岗位介绍文件路径（PDF/Word/TXT/图片） |
| transcript_path | string | 面试文字稿文件路径（PDF/Word/TXT） |

| 输出字段 | 类型 | 说明 |
|---|---|---|
| resume_md | string | 简历Markdown纯文本（已清洗） |
| job_desc_md | string | 岗位介绍Markdown纯文本（已清洗） |
| transcript_md | string | 面试文字稿Markdown纯文本（已清洗） |
| filename_meta | object | 文件名解析结果（见 extract_filename.py） |

**关键逻辑**：
```python
# 伪代码
def parse_files(resume_path, job_desc_path, transcript_path):
    resume_md = markitdown.convert(resume_path)
    job_desc_md = markitdown.convert(job_desc_path)
    transcript_md = markitdown.convert(transcript_path)

    resume_md = text_cleaner.clean(resume_md)
    job_desc_md = text_cleaner.clean(job_desc_md)
    transcript_md = text_cleaner.clean(transcript_md, aggressive=True)

    filename_meta = extract_filename.parse(transcript_path)

    return { resume_md, job_desc_md, transcript_md, filename_meta }
```

#### 5.1.2 extract_filename.py —— 文件名元信息提取
**功能**：从面试文字稿的文件名中，用正则提取「公司/岗位/面试阶段/日期」，提取不到的字段填"待定"。

**支持的文件名格式示例**：
```
字节跳动_AI产品经理_一面_20260820.pdf
腾讯_产培生_二面_2026-08-21.docx
阿里-AI PM-HR面-20260822.pdf
美团面试记录0823一面.pdf        ← 模糊场景，尽量提取
```

| 输出字段 | 类型 | 提取规则优先级 |
|---|---|---|
| company | string | ① 正则匹配分隔符前第一个词块；② 包含常见大厂关键词优先；③ 提取不到→"待定" |
| position | string | ① 正则匹配分隔符后第二个词块；② 包含"产品/经理/PM/运营/研发"等关键词优先；③ →"待定" |
| interview_stage | string | ① 正则匹配"一面|二面|三面|四面|终面|HR面|技术面|业务面|交叉面"；② →"待定" |
| interview_date | string | ① 正则匹配"YYYYMMDD"转"YYYY-MM-DD"；② 匹配"YYYY-MM-DD"原样保留；③ →"待定" |

---

#### 5.1.3 text_cleaner.py —— 通用文本清洗
**功能**：对markitdown转出的Markdown做正则粗清洗，去除无意义内容，减轻LLM负担。

| 清洗项 | 正则规则 | 说明 |
|---|---|---|
| 高频口语填充词 | `(然后|就是|那个|嗯|额|呃|其实|基本上|说实话|好比|那个啥|怎么说呢)[，。,.\s]?` | 非aggressive模式只去独立出现的，aggressive模式（面试文字稿）加强力度 |
| 重复词 | `(.+?)\1{2,}` → `\1` | 如"这个这个这个"→"这个" |
| 多余空行 | `\n{3,}` → `\n\n` | 3个以上空行合并为2个 |
| 断行合并（句子中间换行） | 非段尾的换行合并 | 根据标点判断是否合并 |
| 特殊乱码字符 | 去除控制字符（`\x00-\x1F\x7F`中除换行制表外的） | markitdown偶尔输出的乱码 |
| Markdown噪音 | 移除多余的`#`无意义标题、空表格 | 转PDF时产生的格式噪音 |

---

#### 5.1.4 save_output.py —— 保存输出文件
**功能**：将生成好的Markdown全文写入指定路径，自动处理目录创建和文件名转义。

| 输入参数 | 类型 | 说明 |
|---|---|---|
| markdown_content | string | 最终Markdown全文 |
| company | string | 公司名（用于文件名） |
| position | string | 岗位名 |
| interview_stage | string | 面试阶段 |
| interview_date | string | 面试日期（YYYY-MM-DD 或 待定） |

| 输出 | 说明 |
|---|---|
| saved_path | string | 保存成功的完整绝对路径 |

**关键逻辑**：
1. 基础路径：`/Users/yst/Documents/面试复盘/`
2. `os.makedirs(基础路径, exist_ok=True)` —— 目录不存在则自动创建
3. 文件名组装：`{公司}_{岗位}_{面试阶段}_{面试日期}.md`
4. 特殊字符转义：`/ \ : * ? " < > |` 全部替换为 `_`
5. 空格处理：连续空格替换为单个 `_`
6. "待定"字段保留在文件名中（如`字节_AI产品经理_待定_待定.md`）
7. 写入编码：UTF-8（with BOM？可选，macOS默认不需要BOM）
8. 写入前如果文件已存在，追加 `_v2` / `_v3` 后缀，不覆盖原文件

### 5.2 Prompt层 prompts/

#### 5.2.1 01_extract.md —— 阶段1：面试信息提取
**LLM调用次数**：第1次
**输入**：预处理产物 `{ resume_md, job_desc_md, transcript_md, filename_meta }`
**输出**：符合 `schemas/extracted_data.schema.json` 的JSON

**Prompt核心规则**：
1. **发言人角色推断**：
   - 统计提问次数多的 → 判定为"面试官"
   - 回答/解释多的 → 判定为"候选人"
   - 如果文字稿有明确标注（如"面试官：""候选人："），直接使用标注
   - 如果发言人1/2实在无法区分，保留"发言人1/2"但在文档开头标注
2. **态度信号识别**：
   - 追问："继续说""还有呢""这个点再展开一下"
   - 打断：候选人话没说完面试官就说话
   - 表扬："很好""这个思路不错""回答得挺完整的"
   - 展开引导："不用紧张，慢慢说""可以换个角度想想"
3. **乱码/信号差处理**：
   - 如果某段话明显语义不通但上下文能推断，标注前缀 `【信号推断】`
   - 如果完全无法推断，保留原文但标注 `【信号差，内容可能不准确】`
4. **口语二次过滤**：
   - 尽管脚本层已清洗，仍需留意漏网的填充词
   - 合并"我我我""对对对"这类口吃式重复

**输出格式（严格JSON）**：
```json
{
  "company": "字节跳动",
  "position": "AI产品经理",
  "interview_stage": "一面",
  "interview_date": "2026-08-20",
  "source_confidence": {
    "company_from": "filename|infer|待定",
    "stage_from": "filename|infer|待定"
  },
  "interviewer_qa": [
    {
      "index": 1,
      "question": "先做个自我介绍吧",
      "attitude_signals": [],
      "signal_inferred": false,
      "candidate_answer": "我叫lucky..."
    }
  ],
  "candidate_retro_qa": [
    {
      "index": 1,
      "question": "请问这个岗位的具体汇报线是？",
      "signal_inferred": false,
      "interviewer_answer": "汇报给AI产品组负责人..."
    }
  ],
  "notes": ["其他备注信息，如发言人区分困难等"]
}
```

#### 5.2.2 02_analyze.md —— 阶段2：QA分析打分
**LLM调用次数**：第2次
**输入**：阶段1的 `extracted_data.json` + `resume_md`（简历全文，用于理想回答引用真实经历）
**输出**：符合 `schemas/analyzed_data.schema.json` 的JSON

**Prompt核心规则**：

**A. 问题分类规则**
- **固定分类（优先使用）**：
  1. 自我介绍类
  2. 实习深挖类
  3. 个人项目深挖类
  4. 技术考察类
  5. 产品八股类
  6. 场景题类
  7. 出勤/稳定性问题类
  8. 职业规划类
- **允许AI补充的扩展分类**：压力测试、行为面试（STAR类）、文化匹配、业务理解力考察、逻辑分析考察等
- 每道题**必须**且只能选一个主分类

**B. 5档星级点评标准（严格执行）**

| 星级 | 标准 |
|---|---|
| ★★★★★ | 逻辑完整、证据充分、有终止指标、主动邀请面试官讨论 |
| ★★★★☆ | 主体完整，有明显的可改进点（如少了结尾讨论、某个数据没量化） |
| ★★★☆☆ | 方向对但缺关键内容（通常是终端指标或根源分析，只给了过程没给结果） |
| ★★☆☆☆ | 只给了现象没给分析，或者没有证据支持（空泛陈述） |
| ★☆☆☆☆ | 防御模式、跑偏话题、或者完全没有答到点上 |

- 每个星级点评**必须**附点评理由，说明为什么打这个分
- 点评理由要具体，比如"缺少用户增长数据的量化说明"而不是"不够详细"

**C. 理想回答生成规则**
1. **必须引用简历中的真实经历和数据**，优先对照简历中的项目/实习经历
2. **禁止空泛表达**：不能用"我会……""我认为……"，要用"在XXX项目中，我做了XXX，带来了XXX数据结果"
3. **结尾必须加一句邀请面试官参与讨论的话**，例如：
   - "你觉得这个假设合不合理？"
   - "你在这个业务里是怎么看的？"
   - "如果是你，会怎么优化这个指标？"
4. **结构要求**：理想回答必须包含两部分
   - `framework`（回答框架）：用 bullet point 列出来回答的逻辑结构
   - `full_text`（完整回答文字）：可以直接口述使用的完整一段话
5. **如果简历中找不到可匹配的经历**：
   - `no_resume_match = true`
   - 仍然生成通用的回答框架和示例
   - 在 full_text 开头标注前缀：`【注意】未在简历中找到可直接引用的匹配经历，以下回答为通用框架，建议补充你的实际案例后使用`

**D. 整体评分与失分分析**
- `overall.score`：1-10分，整场面试胜算评估
- `overall.pass`：布尔值，是否通过该场面试（综合判断）
- `overall.reasons`：评估理由，可从以下维度分析
  - 面试时长（太短通常挂，超过40分钟通常有戏）
  - 面试官态度（追问多=有兴趣；打断多=可能不耐烦）
  - 反问阶段面试官回答的详细程度（越详细=越有意向）
- `overall.problems[]`：存在问题列表，分两类
  - **思维型缺陷**：

## 七、容错与边界处理

| 场景 | 处理策略 | 给用户的提示 |
|---|---|---|
| 用户少传了某个文件（缺简历/缺岗位/缺文字稿） | 暂停流程，主动追问用户要 | "检测到缺少【简历PDF/岗位介绍/面试文字稿】，方便补充上传吗？<br>（如果暂时没有简历可以跳过，理想回答部分将以通用框架输出）" |
| 文件格式不支持（如.rar/.zip压缩包 / .pages等） | 暂停流程，主动追问 | "当前文件格式暂不支持，请提供 PDF / Word(docx) / TXT / 图片 格式的面试文字稿~" |
| markitdown解析失败（PDF加密/扫描件不可转文字） | 暂停流程，主动追问 | "【简历PDF/XX文件】解析失败，可能是加密或纯图片扫描件。能否提供可复制文字的版本，或者直接粘贴内容给我？" |
| 面试文字稿完全没有发言人区分（纯段落无1/2标注） | 继续流程但加强推断，文档开头加提示 | 生成的Markdown开头加：`⚠️ 【提示】原始文字稿未标注发言人，QA拆分为AI自动推断，建议手动核对准确性` |
| 面试文字稿中QA数量过少（<3个问题） | 继续流程但加提示 | 文档开头加：`⚠️ 【提示】本次提取到仅X个面试官问题，可能文字稿不完整，请留意` |
| 某个字段完全提取不出来（如公司名） | 填"待定" | 文件名保留"待定"，用户事后自己改 |
| 理想回答找不到简历匹配经历 | 生成通用框架+加【注意】前缀 | 见5.2.2 C.5规则 |
| LLM返回的JSON格式不合法（缺字段/语法错） | 自动重试1-2次，用更严格的格式要求prompt再调用 | 用户无感知，仅内部重试；重试3次失败则提示"AI生成出现异常，请稍后重试" |
| 最终保存时文件已存在 | 自动加_v2/_v3后缀不覆盖 | 用户无感知，保存成功的提示中告知实际文件名 |
